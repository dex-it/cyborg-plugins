## Что делает

Плагин - агент Claude Code для сессий Cyborg. Он знает, как запустить `claude` так, чтобы тот сообщал о себе, и отдаёт терминалу готовое описание запуска; сам терминал, вкладки и процесс держит плагин `sessions`. Что получает человек:

- сессия стартует в оболочке входа (`$SHELL -lc`), поэтому `claude` находится в PATH пользователя, а не только приложения;
- приложение узнаёт, что сессия сменила каталог (ушла в worktree), работает, ждёт ответа, остановилась на вопросе, разрешении или лимите, закончила ход;
- прошлые сессии каталога (и его worktree) видны с заголовками, их можно продолжить и удалить, в том числе несколько разом.

Настройки человека не трогаются: хуки добавляются ключом `--settings` на время сессии, режим разрешений остаётся тем, что выбрал человек.

## Контракты и команды

Плагин отдаёт `cyborg.agent` версии 1.0 (`capabilities`: `resume`, `history`, `events`):

| Член | Что делает |
|---|---|
| `facts` | Находит `claude` (`claude --version` через оболочку входа), отдаёт версию |
| `launch` | Пишет пустой файл событий сессии и описывает запуск: `$SHELL -lc 'exec claude --settings "$CYBORG_SETTINGS" "$@"' cyborg <аргументы>` |
| `watch` | Подписка на события сессии: `cwd`, `session`, `activity`, `prompt`, `turnEnd`, `waiting` |
| `ended` | Убирает файлы сессии и называет причину выхода (`notFound`, `resumeFailed`) |
| `history` | Прошлые интерактивные сессии каталога и его worktree, свежие первыми, до 50 |

Команды (открыты плагинам, на вызывающего действует право на каталог проекта):

- `agent-claude-code.history.list <каталог>` - то же, что `history`;
- `agent-claude-code.history.delete <каталог> <ids>` - удаляет сессии каталога по списку UUID и отвечает `{ deleted, failed }`: сбой одной сессии остальные не останавливает.

### Порядок аргументов

После `--settings` аргументы идут так (FR-9002): `--resume <id>`, `--append-system-prompt <фрагменты>`, `--mcp-config=<файл>` (если есть инструменты плагинов), начальный промпт, `--add-dir <каталоги...>`. Промпт стоит до `--add-dir`: тот вариадический и забрал бы промпт, стоящий после каталогов. Идентификатор для `--resume` проверяется (не флаг, не путь).

### События

Хуки (`SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `Notification`) дописывают JSON события в файл сессии, плагин читает его по смещению:

| Хук | Событие контракта |
|---|---|
| любой, если каталог сменился | `cwd` перед основным событием |
| `SessionStart` с годным `session_id` | `session` (`launch({ resumeId })` её продолжит) |
| `UserPromptSubmit` | `prompt` |
| `PostToolUse`, `PostToolUseFailure` | `activity` с именем инструмента; инструмент субагента (`agent_id`) хода главной модели не меняет и событием не становится |
| `Stop` | `turnEnd`, `background: true`, если есть фоновая задача или расписание |
| `Notification`: `permission_prompt`, `elicitation_dialog`, `elicitation_url_dialog`, `agent_needs_input`, `quota_auto_resume_*` | `waiting` с текстом по типу, без содержимого запроса |

Прочие уведомления (`idle_prompt` и новые типы) событием не становятся. После `turnEnd` без фоновой работы «ждёт» объявляется через 30 секунд, если сессия промолчала: чужой `Stop`-хук мог продолжить ход.

Файл событий называется по `sessionId` потребителя (`sessions/<sessionId>.jsonl`), а не по pid приложения: подхваченная после перезапуска сессия находит свой файл. Первая подписка читает файл с начала, поэтому запись между запуском процесса и взводом наблюдателя не теряется (FR-5003); после взвода наблюдателя файл читается ещё раз. Подписка на сессию, запущенную не этим экземпляром плагина (подхват), начинается с конца файла: прошлое уже показано.

### Причины выхода

`ended` называет причину по коду выхода и содержимому файла событий, без разбора текста вывода claude:

- `notFound` - код 127: оболочка входа не нашла `claude`;
- `resumeFailed` - просили продолжить сессию, `claude` вышел с ошибкой (код больше нуля, не сигнал) и не дошёл до `SessionStart`.

`authRequired` и `rateLimited` плагин не выдаёт: ни код выхода, ни следы хуков их надёжно не отличают, а разбирать текст ошибок контракт запрещает.

## Права

| Право | Зачем |
|---|---|
| `launch`: `$SHELL -lc 'exec claude --settings "$CYBORG_SETTINGS" "$@"' cyborg`, переменные `CYBORG_EVENTS`, `CYBORG_SETTINGS`, `CYBORG_MCP_TOKEN` | Описание запуска, которое плагин отдаёт потребителю. Потребитель запустит его своим правом `pty`; ядро сверяет запуск и с этим правом, поэтому описание шире названного не пройдёт. Скрипт закреплён: меняется только список аргументов |
| `process`: `$SHELL -lc 'claude --version'` | `facts`: найти `claude` и узнать версию. Опасный флаг `--dangerously-skip-permissions` в хвосте отклоняется |
| `fs.read`: `~/.claude/projects` | Список прошлых сессий: журналы Claude Code, заголовок берётся с краёв файла |
| `fs.write`: `~/.claude/projects` | Удаление сессий. **Самое рискованное право плагина - запись, а не чтение.** Плагин пишет (удаляет) только по двум путям сессии: `<каталог журналов проекта>/<uuid>` и `<...>/<uuid>.jsonl`. Идентификатор должен быть UUID (поэтому `..` и разделители не проходят), каталог проекта берётся из листинга `~/.claude/projects` и должен быть каталогом проекта (ссылка наружу не следуется). На всё это есть тесты |

Файлы событий и `claude-hooks.json` лежат в данных плагина, своего каталога данных право не требует.

Окружение: ядро передаёт процессу только PATH, HOME, USER, SHELL, TERM, TMPDIR, локаль и переменные, названные в правиле. Поэтому `CLAUDE*` (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_EFFORT`, ...), `CYBORG_CWD`, `CYBORG_MCP`, `CYBORG_PLUGIN` и прочее окружение приложения или родительской сессии до `claude` не доходят, а в запуске есть только `CYBORG_EVENTS`, `CYBORG_SETTINGS` и (с инструментами плагинов) `CYBORG_MCP_TOKEN`. Токен MCP - в окружении процесса, не в файле и не в командной строке.

Флаги, ослабляющие режим разрешений (`--dangerously-skip-permissions`, `--permission-mode`, `--allowedTools`, `--allowed-tools`, `--disallowedTools`, `--tools`), плагин в запуск не кладёт; их запрет в хвосте argv несёт правило `pty` потребителя (`sessions`, M-03): у правила `launch` поля `deny` нет.

## Настройки

Раздела `config` и `state` нет.

## Как проверено

Тесты идут на `startKernel` и общем наборе `agentContractSuite` из тест-кита ядра, с подставными `claude` и `$SHELL` из `@cyborg-plugins/fixtures` (события хуков в `CYBORG_EVENTS`) и подставным каталогом настроек Claude как домашним. Описание запуска исполняется целиком: подставная оболочка входа, `--settings`, `"$@"`, подставной `claude`. **На живом `claude` плагин не проверялся**: расхождения с версией Claude Code (имена хуков, форма журналов) может выявить только живой прогон.

## Ограничения и отложенное

- **Вид «Сессии проекта»** (`history:list`, `history:delete` по `projectId`, выделение, подтверждение, клавиатура: FR-8001..8005) отложен до появления контракта `cyborg.projects`: список по проекту собирается из репозиториев проекта. Здесь сделано то, что от проекта не зависит: `history(cwd)`, команды `history.list` и `history.delete` по каталогу, продолжение через `resumeId`.
- **Контекст вкладки** (название разговора из журнала, первый и последний запрос): в `AgentEvent` нет такого события, подсказку вкладки (`session-context`) без расширения контракта не перенести.
- **Права файлов 0600 и каталога 0700** (ai-cyborg сужал их): `ctx.os.fs` режим не задаёт, файлы событий лежат в каталоге данных плагина с правами по умолчанию.
- **Файлы убитого приложения**: pid в имени файла больше нет, поэтому при активации удаляются файлы сессий старше недели; свежие остаются (сессия могла дожить до перезапуска).
- **Плагин Claude Code Cyborg** (`--plugin-dir`, скиллы, хук `lsp-reap`) и `report_done` - задачи M-04; здесь их нет.
- **Запуск на SSH-хосте** - M-05.
- `authRequired` и `rateLimited` - см. выше.
