## Что делает

`sessions` - сердце рабочего места: открывает сессию агента (сегодня Claude Code) в терминале ядра, держит её вкладкой окна, следит за её состоянием и отдаёт остальным плагинам события и управление. Главная часть, о которой говорит эта страница, включает **делегирование дочерним сессиям с MCP-сервером** (M-04, раздел ниже); **вид** (вкладки в окне, xterm.js, порядок и перетаскивание вкладок, ссылки в выводе, размер шрифта, бросок пути на терминал, заголовок окна) - отдельная часть задачи (см. «Ограничения»).

Что делает главная часть:

- **Открывает сессию** в репозитории проекта. Каталоги (рабочий и дополнительные, `--add-dir`) проверяются по проектам `cyborg.projects`: вне репозиториев проектов сессия не стартует. Агент берётся из поставщиков `cyborg.agent` (названный или первый найденный по порядку id), запуск идёт в pty ядра с `persist`, размер 120 на 40.
- **Собирает системный промпт** из фрагментов всех поставщиков `cyborg.session-prompt` (сегодня `session-isolation`, позже `next-actions`) и отдаёт их агенту при запуске.
- **Переводит события агента** в события сессии: каталог сменился (в том числе в worktree), агент работает, агент ждёт человека (вопрос, разрешение, лимит, конец хода), процесс вышел. Тексты запросов и ответов в события не идут.
- **Принимает ввод** от чужих плагинов (`send`, `paste`) с теми же пределами, что у ai-cyborg: id сессии, ввод не больше 1 МиБ, размер терминала 1..1000.
- **Держит метки** сессии: привязку к задаче и MR трекера - только в памяти (FR-1015, FR-2014).
- **Поручает работу другим сессиям**: у каждой сессии, запущенной отсюда, есть MCP-сервер Cyborg с инструментами `open_session`, `list_sessions`, `send_to_session`, `close_session`, `report_done` и инструментами поставщиков `cyborg.agent-tool`; модель открывает дочерние вкладки в фоне, пишет им, получает итог и закрывает отработавших.
- **Возвращает сессии**: процесс живёт в pty-хосте ядра и переживает перезапуск хоста плагина и окна (плагин подхватывает оставленные pty при активации); вышедшая сессия остаётся вкладкой и продолжается вручную.

## Контракты

**Отдаёт `cyborg.sessions` 1.2** (кратность one). Типы версий 1.0 и 1.1 (`onChange`, `reveal`) есть в ядре, члены 1.2 в ядре пока не объявлены ([cyborg-harness#257](https://github.com/dex-it/cyborg-harness/issues/257)), поэтому их объявляет пакет [`contracts/`](https://github.com/dex-it/cyborg-plugins/tree/master/contracts) этого репозитория отдельным интерфейсом `SessionsV12`, расширяющим интерфейс ядра (решение 11 в [решениях по переносу](/development/decisions/)). Потребитель берёт поставщика как `Remote<SessionsV12>` и проверяет, что нужный член есть: поставщик 1.0 и 1.1 их не даёт.

| Член | Что делает |
|---|---|
| `onChange(listener)` | События всех сессий: `cwd`, `activity`, `waiting`, `exit`; прошлое не повторяется; слушатель, бросивший исключение, соседям не мешает |
| `reveal(sessionId)` | Открыть вкладку сессии в окне; вышедшая сессия тоже открывается, закрытая человеком - отказ |
| `create(request)` | Открыть сессию: каталоги, запрос, агент, `resumeId`, привязка с первого кадра; ответ - `{ sessionId, title }` |
| `send(sessionId, text)` | Ввод как с клавиатуры (перевод строки - Enter); не больше 1 МиБ |
| `paste(sessionId, text, { submit })` | Вставка в строку ввода агента (bracketed paste); управляющие символы из текста убираются, `submit` отправляет Enter отдельной записью через 150 мс |
| `labels(sessionId)`, `setLabels(sessionId, patch)`, `find(kind, key)` | Привязка сессии к задаче (`task`) и MR (`mr`): поставить, снять (`null`), найти живую сессию объекта; объект трекера - у одной сессии |
| `uses(root)` | Идёт ли живая сессия, запущенная с этим каталогом (рабочим или из `--add-dir`): git не меняет ветку под работающей сессией |

**Потребляет** `cyborg.agent` (many), `cyborg.session-prompt` (many) и `cyborg.agent-tool` (many); **требует** `cyborg.projects`. Инструменты `cyborg.agent-tool` агенту отдаёт тот же MCP-сервер, что и инструменты сессий (раздел «Делегирование»).

### Метки в памяти

Привязка задачи и MR к сессии живёт только в памяти плагина: не в документе вкладки, не в `state`, не в файлах данных. После перезапуска приложения её нет, трекер ставит её заново. Тест перебирает документы, состояние и все файлы данных плагинов на отсутствие названий и статусов привязанных задач. Выход процесса снимает привязку (задача снова без сессии), закрытая вкладка забирает метки с собой.

### Порядок фрагментов промпта

В ai-cyborg инструкция изоляции идёт первой, кнопки следующих шагов после неё. Ядро сегодня не знает порядка фрагментов, поэтому `sessions` собирает их **по id плагина-поставщика**: `next-actions` стоит раньше `session-isolation`, то есть изоляция второй. Это решение владельца (D-00, п. 3) до появления явного `order` в ядре ([cyborg-harness#259](https://github.com/dex-it/cyborg-harness/issues/259)); расхождение записано в allowlist матрицы паритета (FR-9001). Текст изоляции дословный, порядок зафиксирован тестом. Пустой вклад отбрасывается, сломанный поставщик запуску не мешает.

## Делегирование дочерним сессиям (фича 15, M-04)

Сессия-руководитель поручает части задачи соседним вкладкам и забирает итог. Модель видит инструменты MCP сервера `cyborg`; порядок работы с ними ей подсказывает скилл `cyborg:parallel-sessions` плагина Claude Code, который `sessions` подключает к каждой своей сессии.

### Сервер и токены

- Сервер поднимается по праву `serve` с первой сессией: JSON-RPC в `POST /mcp`, один ответ JSON на запрос, потока SSE нет (`GET` - 405, уведомления клиента - 202). Слушает только `127.0.0.1`; запрос с Origin страницы браузера и с чужим Host ядро отсекает до плагина.
- **Принимает только сессии Cyborg по их токену** (NFR-15001): без токена, с чужим и после выхода сессии - 401. Токен у каждой сессии свой, 32 случайных байта (43 знака base64url).
- **Токены хранит и отзывает `sessions`** (решение 13 в [решениях по переносу](/development/decisions/)): они только в памяти плагина. Токен отзывается, когда процесс сессии вышел, вкладку закрыл человек или инструмент `close_session`, а также если запуск не удался.
- **Токен нигде не лежит на диске и не в аргументах.** Его получает процесс агента переменной окружения `CYBORG_MCP_TOKEN`; конфиг MCP, который пишет `agent-claude-code` (`--mcp-config=<файл>`), содержит адрес сервера и ссылку `Bearer ${CYBORG_MCP_TOKEN}`, но не значение. Поэтому права `0600` для файла с токеном не нужны: в ai-cyborg токен лежал в файле `0600`, шлюз ядра не умеет задавать права файла, а хранить секрет в файле незачем. Тест перебирает аргументы запуска, все файлы данных и дома, журнал ядра и плагина, документы и ответы команд на отсутствие токена (аналог T-05 ядра).
- Порт выбирает ОС, поэтому после перезапуска **хоста плагина** оставленные (подхваченные) сессии прежний сервер не находят: их конфиг указывает на старый порт и MCP у них не работает до следующего запуска сессии. Новые сессии получают новый сервер и видят подхваченных в `list_sessions`.

### Инструменты

| Инструмент | Что делает | Кто может вызвать |
|---|---|---|
| `open_session` `prompt`, `repo` | Открывает вкладку в том же проекте в фоне (текущая остаётся активной), `prompt` - первое сообщение; остальные каталоги проекта подключаются как `--add-dir`. Ответ: «Открыта вкладка сессии N в repo.» | Любая сессия |
| `list_sessions` | Вкладки проекта вызывающей, она сама с `self: true`: номер, `tab` (`CC<n>`), `parent`, `child`, `repo`, `cwd`, `state` (`starting`, `working`, `waiting`, `asking`), `reason`, `queued`, `last_answer` (хвост до 1500 знаков) | Любая |
| `send_to_session` `id`, `message` | Пишет в другую вкладку вставкой и Enter отдельной записью. `waiting` и молчание 2 с - сразу, `working` - в очередь до конца хода, `starting` и `asking` - отказ. Слэш-команды, «!», «#» и себе - отказ | Любая |
| `close_session` `id`, `force` | Закрывает вкладку как крестик: документ, процесс, очередь. Свою дочернюю - всегда; ждущую соседку - без `force`; работающую, запускающуюся и ждущую человека - только с `force: true`; себя - через секунду после ответа | Любая |
| `report_done` `status`, `summary`, `branch`, `pr` | Сдаёт итог открывшей сессии сообщением в её очередь; один за круг работы, новый круг - со следующего запроса. Открывшей нет - уведомление рабочего стола | Только дочерняя (открытая через `open_session`) |

Инструменты поставщиков `cyborg.agent-tool` идут следом за своими, под тем же токеном: имя из `[A-Za-z0-9_-]`, повтор и имена своих инструментов отброшены с записью в журнал; результат с `isError` доходит до модели как ошибка, кнопки (`actions`) хранятся до следующего запроса человека (команда `sessions.actions`) и уходят виду сообщением `actions`. Описание инструмента попадает в контекст агента до вызова, поэтому контракт `cyborg.agent-tool` отдают только плагины поставки (правило ядра).

### Как открывается вкладка по поручению

Модель вызывает `open_session`; плагин заводит поручение с **одноразовым ключом** и держит текст задания у себя. Вкладку по ключу открывает сам плагин (документы-вкладки его), поэтому в отличие от ai-cyborg, где ключ шёл окну, ни ключ, ни промпт до вида не доходят: виду уходит сообщение `session:handoff` с номерами (`from`, `sessionId`, `number`), а при закрытии - `session:close`. Не удалось открыть (каталог больше не в проекте, агент не найден, нет `cyborg.projects`) - причина (до 500 знаков) возвращается модели ошибкой инструмента, это путь канала `session:handoffFailed`. Ожидание - 20 с.

### Состояние сессии

Состояние считается по событиям агента (`cyborg.agent.watch`), а не по тексту вывода: `starting` до начала сессии агента, `working` на запросе человека и работе инструмента, `waiting` в конце хода (с фоновой работой - всё ещё `working`), `asking` на вопросе, разрешении или лимите. Подхваченная после перезапуска хоста сессия остаётся `starting`, пока не придёт первое событие: ей не пишут. Очередь сообщений живёт в памяти и пропадает с вкладкой.

### Родитель и «семья»

У вкладки, открытой инструментом, в данных документа есть `parent` (id сессии-родителя), `parentNumber` и `family` (id корня семьи); у открытой человеком `family` - она сама. Команда `sessions.family` отдаёт виду по живым вкладкам `{ sessionId, doc, number, label, parent?, parentNumber?, family }`, где `label` - подпись `CC2 ↳1`. **Цвет «семьи» рисует вид**: у всех вкладок с одним `family` цвет один. Родитель закрыт - подпись и семья у дочерней остаются. Номера разговоров Claude Code, открытых другой сессией, плагин пишет в `child-sessions.json` (последние 2000, команда `sessions.children`): по ним «История» помечает дочерние.

### Плагин Claude Code `cyborg`

Скилл `parallel-sessions` и хук `lsp-reap` (перезапуск языкового сервера после смены или снятия worktree) лежат в `assets/` плагина и вшиты в `index.mjs` (`npm run embed-assets`, решение SP-02 в [руководстве автору](/authors/assets/)). При активации плагин записывает их в каталог данных (`<данные плагина>/assets/<версия>/`, без бита исполнения: хук вызывается как `bash "${CLAUDE_PLUGIN_ROOT}/hooks/lsp-reap.sh"`) и подключает каждой своей сессии ключом `--plugin-dir=<каталог>` только на время сессии: настройки Claude Code не меняются. К системному промпту дописывается повод к делегированию со ссылкой на скилл, когда у сессии есть и MCP, и плагин.

## Команды

Команды открыты виду плагина (и человеку); остальные плагины работают через контракт.

| Команда | Канал ai-cyborg | Что делает |
|---|---|---|
| `sessions.create` `{ cwd, addDirs?, prompt?, agent? }` | `session:create` | Открывает сессию; ответ `{ sessionId, title, ticket }`, билет - для терминала вида |
| `sessions.resume` `{ cwd, addDirs?, resumeId, agent? }` | `session:resume` | Продолжает прошлую сессию из истории агента; нет в истории - отказ |
| `sessions.kill` `id` | `session:kill` | Завершает процесс сессии |
| `sessions.write` `id, data`, `sessions.resize` `id, cols, rows` | - | Ввод и размер с теми же проверками; терминал вида пишет в pty напрямую (`session:input` и `session:resize` решает pty-хост ядра) |
| `sessions.agents` | - | Агенты и их факты |
| `sessions.previous`, `sessions.running` | - | Вкладки без процесса (ждут восстановления) и идущие сессии |
| `sessions.reopen` `документ` | - | Новый билет на идущую сессию: окно после перезагрузки подключает терминал заново |
| `sessions.restore` `документ` | - | Восстановление вручную: вышедшая сессия стартует в той же вкладке и продолжает разговор агента (`--resume`) |
| `sessions.family` | - | Номер, подпись `CC<n> ↳<родитель>`, родитель и семья живых вкладок (для вида) |
| `sessions.children` | - | Номера разговоров Claude Code, открытых другой сессией (для «Истории») |
| `sessions.actions` `id сессии` | - | Кнопки, предложенные инструментом поставщика, пока их не сняло следующее сообщение человека |

Негодные аргументы `write`, `resize` и `kill` молча отбрасываются (мусор из вида не роняет плагин), `send` и `paste` отказывают с причиной.

## Права

| Право | Зачем |
|---|---|
| `pty`: `$SHELL -lc 'exec claude --settings "$CYBORG_SETTINGS" "$@"' cyborg`, переменные `CYBORG_EVENTS`, `CYBORG_SETTINGS`, `CYBORG_MCP_TOKEN`, **запрещены флаги** `--dangerously-skip-permissions`, `--permission-mode`, `--allowedTools`, `--allowed-tools`, `--disallowedTools`, `--tools` | Запуск агента в терминале. Правило закреплено: то же, что объявил `agent-claude-code` в `launch`. У `launch` поля `deny` быть не может, поэтому запрет флагов, ослабляющих режим разрешений, несёт это правило: ни агент, ни запрос человека не проведут такой флаг в запуск. Запрос, равный запретному флагу, ядро тоже отклоняет |
| `serve` | MCP-сервер сессий на `127.0.0.1` с портом от ОС: агент зовёт инструменты по HTTP. Принимает только запросы с токеном сессии Cyborg |
| `notify` | Итог дочерней сессии, когда открывшей её сессии уже нет (`report_done`): уведомление рабочего стола «CC2», «статус: начало итога» |
| `fs.read`: `workspace` | Ядро проверяет рабочий каталог pty как чтение. Область `workspace` - репозитории проектов (их задаёт `projects`) и рабочие каталоги живых сессий. **Файлов плагин не читает**: право нужно, чтобы сессия могла стартовать в репозитории проекта. Другие каталоги не открыты |

Окружение процесса сессии - только то, что назвало правило (`CYBORG_EVENTS`, `CYBORG_SETTINGS`, `CYBORG_MCP_TOKEN`), плюс базовое окружение ядра (PATH, HOME, локаль, TERM). Переменные приложения и родительской сессии (`CLAUDE*`, `CYBORG_CWD`, `CYBORG_MCP`, `CYBORG_PLUGIN`) до агента не доходят: тест проверяет. Каталог плагина Claude Code идёт не переменной `CYBORG_PLUGIN`, как в ai-cyborg, а ключом `--plugin-dir=<каталог>` в аргументах запуска сразу за именем скрипта: переменная потребовала бы правки скрипта и правила `launch` у `agent-claude-code`, а путь к каталогу - не секрет.

Документ вкладки хранит id сессии, плагин-агент, каталоги запуска, id разговора для `--resume`, пару «id:pid» процесса и, у дочерней, `parent`, `parentNumber` и `family`. Метки, запрос и вывод в нём нет.

## Как проверено

Тесты идут на `startKernel` и настоящих `agent-claude-code` и `session-isolation` (подставные `claude` и оболочка входа из `@cyborg-plugins/fixtures`), терминал - `fakePty()` тест-кита, хуки изображает запись строки JSON в файл событий сессии. **На живом `claude`, настоящем node-pty и в окне плагин не проверялся.** Что MCP-клиент настоящего `claude` пройдёт рукопожатие (`initialize`, `tools/list`, `tools/call` с заголовком из `${CYBORG_MCP_TOKEN}`) и что он примет `--plugin-dir=` с `=`, подтверждено только подставным клиентом тестов; ручная проверка на живом - открытый пункт.

Делегирование: тесты `mcp.test.ts`, `session-tools.test.ts`, `child-sessions.test.ts` и `lsp-reap.test.ts` перенесены из ai-cyborg с теми же утверждениями (отличия названы в шапке каждого файла); `delegation.test.ts` держит состояние, очередь и итог дочерней (перенос утверждений `SessionManager.say`, `enqueue`, `reportLocal`); `mcp-server.test.ts` - сценарий S19 и остальное на настоящем ядре, настоящем HTTP и подставном терминале (токены, инструменты поставщиков, открытие, перечень, ввод, закрытие, итог, подхват); `delivery.test.ts` собирает плагин настоящим `cyborg-plugin build`, запускает его на ядре и исполняет хук настоящим `bash`. Второй тест `lsp-reap` читает `/proc` и идёт только на Linux, как в ai-cyborg.

## Ограничения и отложенное

- **Вида нет.** Вкладки как документы окна ядро создаёт, но показывать их нечем: xterm.js в `<iframe>`, поиск, ссылки в выводе (`term-links`), режимы терминала (`term-modes`), порядок, перетаскивание и «семья» вкладок, возврат к панели, заголовок окна (`title`), размер шрифта (`cyborg.fontSize`), бросок пути на терминал (`drop-path`), Shift+Enter, выделение и буфер обмена - второй PR задачи M-03.
- **Заголовок вкладки** сейчас `Claude Code <номер запуска>`; сборку заголовка «CC1 · #12 Название · открыта» из меток берёт вид.
- **Контекст вкладки** (`session:context`: название разговора, первый и последний запрос) не перенесён: в `AgentEvent` такого события нет, а тексты запросов в события сессий по решению не идут.
- **Удалённые агенты по MCP** (`spawn_agent`, `close_agent`, хосты проекта, `host` и `link` в `list_sessions`, туннель MCP к SSH-хосту) - M-05: у `sessions` их нет, а скилл `parallel-sessions` упоминает их как доступные «если в проекте заданы хосты».
- **Подхваченные сессии без MCP после перезапуска хоста плагина:** порт сервера выбирает ОС, конфиг сессии указывает на старый. Нужен стабильный порт или переподключение в ядре.
- **Очередь сообщений и итог для открывшей сессии - только в памяти** этого запуска приложения.
- **Живой `claude` не проверялся**: протокол MCP, `--plugin-dir=` и выполнение хука его процессом проверены на подставном клиенте и `bash` (см. «Как проверено»).
- Prompt injection через итог дочерней сессии: итог приходит родителю сообщением как ввод человека; границы описаны в SAD ядра, проверки на живом агенте нет.
- **Удалённые сессии** по SSH - M-05, уведомления - M-07 (они уже ждут `onChange` и `reveal` отсюда).
- **Восстановление после перезапуска приложения - только вручную** (D-00, п. 6): вкладка прошлого запуска ждёт `sessions.restore`, процесс сам не стартует.
- Вкладка нумеруется с единицы в каждом запуске приложения; после перезапуска у восстановленной вкладки сохраняется прежний заголовок, у новой номер может повториться.
- Факты агента (`claude --version` через оболочку входа) кэшируются на минуту: пилот ядра показал, что лишний процесс на каждый запуск - четверть времени старта сессии.
- Нагрузочный сценарий «вывод 50 000 строк» относится к виду и pty-хосту ядра: плагин в потоке вывода не участвует (вывод идёт из pty-хоста во фрейм мимо хоста плагина), поэтому здесь его не измеряют.
